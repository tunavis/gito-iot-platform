# Design — Expo mobile client

## Context

Two constraints drive every decision here, and they pull in the same direction:

1. **The primary author is a non-developer working through AI assistance.** Code
   quality is whatever the model produces, so the stack should be the one models
   write best, and correctness should be enforced by tooling that fails loudly
   rather than by conventions a reviewer has to notice.
2. **The platform must be unreachable from this work.** The mobile app is a pure
   consumer. There is no task in this change that opens a file under `api/`,
   `web/`, `processor/`, `shared/`, or `db/`.

A third, weaker constraint: the maintainer has ~2h/day and reviews everything.
Anything that needs deep review per commit is a bottleneck. Type errors and a
schema-drift check catch the common failure modes without a human reading every
line.

## Decisions

### Expo (React Native) + TypeScript, not Flutter

Rejected Flutter despite it being what the deleted app used and despite its
genuinely better desktop story — desktop is not a target, so that advantage is
worth nothing here.

| | Expo/RN | Flutter |
|---|---|---|
| iOS / Android quality | native views | own renderer, equally good |
| Language shared with `web/` | ✅ TypeScript | ❌ Dart |
| Contributor's first run | `npx expo start` + phone | Flutter SDK + Android Studio/Xcode |
| AI code quality | high (largest TS/React corpus) | lower |
| Apple's Liquid Glass | real `UIVisualEffectView` via `expo-blur` | must imitate it |
| Desktop | weak | strong (not a target) |

The Liquid Glass point is the one that inverts intuition. Flutter paints every
pixel itself, so a system material is something it approximates and re-approximates
each time Apple revises it. `expo-blur` binds the actual native material. For a
design brief that names Apple's language explicitly, the native-view stack is the
higher-fidelity one.

The AI-quality point is not a soft preference — given who is writing this, the
model's competence in the language *is* the app's competence.

### API types are generated from a committed OpenAPI schema, never hand-written

Two artifacts are committed: `openapi.json`, produced from the FastAPI app
itself (import the app, call `app.openapi()` — no running server involved), and
`mobile/src/api/schema.d.ts`, produced from that file by `openapi-typescript`.
The typed client resolves paths and response types from the latter.

**Generating from source rather than from a live server is deliberate, and it is
what makes two-person parallel work safe.** If types were generated by hitting a
running API, the contributor's types would reflect whatever containers he
happened to have up — an older migration state produces stale types that look
authoritative and that nobody can distinguish from correct ones. Generated from
source, the schema is a property of the commit. The contributor gets the right
types by pulling `main`, not by having the right stack running.

CI enforces the pair: a pull request that changes a router without regenerating
`openapi.json` fails. So `main` always carries a schema that matches its own
code, and the mobile app can trust it without coordination.

This is the change's central mechanism, and it is chosen over the two obvious
alternatives:

- **Hand-written interfaces** — what the Flutter app did. Every response shape
  existed twice, and the copy drifted silently. A renamed field surfaced as
  `undefined` on a screen, at runtime, on someone's phone.
- **A full SDK generator** (openapi-generator and friends) — produces a large
  generated client with its own opinions about auth, retries, and errors, which
  then fights `@tanstack/react-query`. Types are the valuable part; the runtime
  is not.

What this buys, concretely: an invented endpoint or a misremembered field name is
a **compile error**, not a runtime 404 or a blank card. That is the difference
between a guardrail a reviewer must enforce and one the toolchain enforces.

`schema.d.ts` is committed (so a clone builds without a running API) and a task
adds a drift check — regenerate, fail if the diff is non-empty — so a backend
change cannot quietly desynchronise the mobile app.

### `expo-router` for navigation

File-based routing, so `mobile/app/devices/[id].tsx` is the device detail route.
Chosen over React Navigation's imperative configuration specifically because it
mirrors `web/src/app/` — the same mental model, the same dynamic-segment syntax.
Patterns transfer from the web app in both directions, which matters when the
maintainer reviews both.

### `@tanstack/react-query` for server state

Caching, retry, background refetch, and invalidation are the bulk of what a
client like this does, and they are where hand-rolled `useEffect` fetching goes
wrong — double fetches, races, stale screens after a mutation. React Query is
already the default in the React ecosystem and models are fluent in it.

No Redux, no Zustand. There is very little client state here that is not either
server state (React Query owns it) or auth state (one context).

### Styling: a typed token module, not NativeWind

This one is close, and worth recording why it went the way it did.

NativeWind (Tailwind for React Native) would match `web/`'s Tailwind and models
write Tailwind extremely well. It was rejected on one specific point: a Tailwind
class is a **string**. `className="p-4 bg-white/10"` is an inline magic value that
TypeScript cannot check — an off-token colour or an invented spacing step compiles
fine. `theme.spacing.md` does not; a typo fails the build.

The whole change is built on *the type system enforces correctness*. Styling has
to obey the same rule or the requirement about no inline literals becomes a thing
a reviewer must police by eye. Secondary benefit: no Babel/Metro configuration to
break on an Expo SDK upgrade, which the contributor could not debug.

### Motion, glass, and haptics

- `react-native-reanimated` — animations on the UI thread, so they hold 60fps
  while JS is busy fetching. Non-negotiable for the physics feel requested.
- `react-native-gesture-handler` — follow-your-finger interactions.
- `moti` — declarative layer over Reanimated (`from` / `animate` props). Included
  specifically because its API is far easier for a non-developer to use correctly
  than raw shared values and worklets.
- `expo-blur` — native materials for the glass surfaces.
- `expo-linear-gradient` — gradients.
- `@shopify/react-native-skia` — **only** where a gradient cannot do it: mesh
  gradients and glow. It is a heavy dependency; it is not the default drawing
  layer.
- `expo-haptics` — one wrapper helper, not called ad hoc per screen.
- `@gorhom/bottom-sheet` — the floating-card presentation model.
- `@shopify/flash-list` — the device list is 68 rows today and should not be the
  thing that breaks at 5,000.

Spring configurations live in the theme as motion tokens, so "how the app feels"
is tunable in one file rather than re-derived per screen. Reduce-motion is honoured
in the shared primitives — once, not per screen.

### Dashboard widgets: read-only, web's contract

Mobile reads `widget_type` and `configuration` exactly as stored and renders the
subset it implements. It does not write widget configuration in Phase 1 and does
not invent config fields.

An unimplemented `widget_type` renders an explicit placeholder naming the type.
This is deliberate and is the opposite of what the Flutter app did — there, an
unknown type fell through a switch to whatever the wildcard case happened to do,
which is how `map` and `table` came to be "not implemented" without anyone
noticing on screen.

### Verification: types and drift, not a component suite

A full component-test suite authored by a non-developer would be maintenance
weight with little signal. What is worth automating is the failure mode that will
actually happen:

- `tsc --noEmit` — catches invented endpoints, wrong field names, off-token
  styling. This is the real gate.
- Schema-drift check — regenerate types, fail on a non-empty diff.
- ESLint with a rule set that forbids raw colour literals and `fetch` outside the
  API layer, so two of the spec's requirements are machine-checked rather than
  reviewed by eye.
- A small Jest suite for the pure functions only: JWT decode, telemetry value
  formatting, widget config resolution. These are the bits with branches.

## Structure

```
mobile/
├── app/                          # expo-router: files are routes
│   ├── _layout.tsx               # providers: query, auth, theme
│   ├── (auth)/login.tsx
│   ├── (tabs)/
│   │   ├── index.tsx             # dashboards
│   │   ├── devices.tsx
│   │   └── alarms.tsx
│   ├── devices/[id].tsx
│   └── dashboards/[id].tsx
├── src/
│   ├── api/
│   │   ├── schema.d.ts           # GENERATED — never hand-edited
│   │   ├── client.ts             # typed fetch + auth header + 401 handling
│   │   └── hooks/                # one file per resource, react-query
│   ├── auth/                     # secure-store, JWT decode, context
│   ├── theme/                    # tokens: colour, glass, motion, spacing
│   ├── ui/                       # GlassCard, Button, Loading/Empty/Error
│   ├── widgets/                  # dashboard widget renderers
│   └── lib/
├── app.config.ts                 # base URLs from env
├── .env.example                  # committed; .env is not
├── CLAUDE.md                     # guardrails for AI sessions in mobile/
└── ONBOARDING.md                 # Windows setup + workflow
```

`app/` holds routes and nothing else — screens compose from `src/`. This keeps
"where does this go" answerable without judgement, which matters for a
contributor who cannot yet rely on instinct.

## Contributor workflow

```
  ┌──────────────────────────────────────────────────────────┐
  │  Mike's loop                                             │
  │                                                          │
  │  git checkout -b mobile/<task>                           │
  │            │                                             │
  │            ▼                                             │
  │  open next unchecked task in tasks.md                    │
  │            │                                             │
  │            ▼                                             │
  │  AI implements it (scope = that task only)               │
  │            │                                             │
  │            ▼                                             │
  │  npx expo start  →  scan QR  →  see it on his phone     │
  │            │                                             │
  │            ▼                                             │
  │  npm run check   (tsc + lint + drift)                   │
  │            │                                             │
  │            ▼                                             │
  │  tick the box, commit, push, open PR ──▶ Mark reviews    │
  └──────────────────────────────────────────────────────────┘
```

Three properties matter:

- **One task at a time.** `tasks.md` is ordered and each task is small enough to
  finish in a sitting. The task list is the scope boundary — it never sends him
  outside `mobile/`.
- **He sees it on a real phone immediately.** No emulator, no native toolchain,
  no `proxy.py`. This is the single biggest reason a non-developer stays engaged.
- **Nothing lands unreviewed.** Branch, PR, maintainer merges.

`mobile/CLAUDE.md` carries the rules into every AI session started in that
directory: no hardcoded values, no mock data, no touching the platform, the API
contract, and the token/tenant pattern. It is the mechanism by which the
guardrails survive the maintainer not being in the room.

## Two people working in parallel

The maintainer works on `api/` and `web/`; the contributor works on `mobile/`.
Both use OpenSpec. Three mechanisms keep them coherent, and none of them is
"remember to tell the other person".

**One repository is the documentation channel.** API code, `openspec/specs/`,
root `CLAUDE.md`, and archived changes all arrive together on `git pull`. There is
no second place to look and nothing to subscribe to.

**A platform change becomes a mobile compile error, not a memo.** This is what
the committed schema buys. A renamed field lands on `main`; the contributor pulls;
`npm run check` fails at every affected call site and that failure list *is* the
work. Compare the real precedent: `ttn_app_id` → `lorawan_app_id` (migration 032)
was breaking. A hand-written client would have compiled fine and rendered blanks.

**OpenSpec changes do not collide, because each is its own directory.**
`openspec/changes/rebuild-mobile-app/` and whatever the maintainer has in flight
touch different files. Archiving folds deltas into `openspec/specs/`, so a change
to `device-management` reaches the contributor as a spec update on his next pull.

The one thing that would break this is the mobile spec restating platform
behaviour, because then the copy drifts. It deliberately does not: it says
"reads from the existing dashboard endpoints" and "the same `configuration` keys
the web widget reads" — it points at the contract rather than duplicating it, so
a platform change cannot make the mobile spec wrong. Where the mobile app needs
something the platform does not offer, the requirement is to raise a separate
change, not to absorb it.

Human conventions still required, both already in use here:

- **Breaking changes carry `!` in the commit subject** (`refactor(devices)!:`,
  `feat(notifications)!:`). It is the signal the contributor's `git log` shows him.
- **`main` is pulled before starting each task**, not once a week. Small merges
  beat one large reconciliation, and the contributor cannot resolve a large one.

## Deferred, explicitly

Not in this change, and — per the "absent, never stubbed" requirement — with no
placeholder UI either:

- Device commands and the approval flow (role-restricted; needs its own thought
  about how a phone should present an approval)
- OTA firmware campaigns
- Notifications and push
- Settings, user management, organizations, sites, hierarchy
- Analytics screens
- Device digital-twin visualisation (the Flutter app's half-built HMI renderers)
- Dashboard *editing* — mobile is read-only for dashboards in Phase 1
- Offline write queue. Reads may cache via React Query; writes require a
  connection. An offline mutation queue is a correctness problem (conflict
  resolution against alarm state that moved on) and does not belong in a first
  change.

## Risks

- **Expo SDK upgrades move fast** and can break native dependencies. Mitigated by
  keeping the dependency list small, preferring Expo-maintained modules, and
  pinning the SDK. The contributor should never be the one debugging a Metro
  config — an SDK upgrade is a maintainer task.
- **The contributor cannot judge whether generated code is reasonable.** This is
  the real risk and it is not fully solvable. Mitigated by: small tasks,
  machine-checked constraints, PR review, and a spec that states the invariants
  in terms a reviewer can check quickly.
- **iOS builds need a Mac or EAS.** Expo Go covers all of Phase 1 on Windows. A
  real App Store build later needs EAS Build (cloud, no Mac) or a Mac. Not a
  Phase 1 blocker, but it is a known cost that arrives before shipping.
- **The API's OpenAPI schema must be accurate.** If a route's response model is
  loosely typed, generated types will be loose too and the guarantee weakens
  there. Where that shows up, it is a finding to report — not something the
  mobile app should paper over.
