## Why

If the pilot in `add-spatial-scene-viewer` shows that the existing SVG device twins
do not carry a site scene convincingly, the scene layer needs real artwork: a kit of
pre-rendered isometric objects that a customer recognises as their own site. The
reference product (Genergy's Home Assistant dashboard) wins on artwork and loses on
composability — it ships one fixed house of stacked PNGs and needs a manual cable
editor because the art cannot move. A kit of interchangeable pieces beats it, but
only if the pieces look like one set.

The single failure mode of an asset kit is **drift**: forty assets that each look
fine alone and wrong together. Drift is not fixable after the fact — it is prevented
by a binding specification agreed before anything is generated, modelled or bought.
This change is that specification plus the production pipeline around it.

**This change is gated.** It does not start until `add-spatial-scene-viewer` task 7.4
records a customer verdict. If the SVG twins are good enough at scene scale, this
change is closed unimplemented and the money is not spent.

## What Changes

- **A binding art specification** — camera, lighting, output, anchoring, material
  palette and rejection criteria, normative for every asset regardless of whether it
  is 3D-rendered, illustrated or generated by an image model.
- **A footprint sidecar format** — per-asset JSON declaring footprint, height,
  anchor, sockets and overlay zones, because a renderer cannot infer any of that
  from a PNG. This is the same object interface the SVG templates expose in
  `add-spatial-scene-viewer`, so a scene can consume either source.
- **Raster objects as a second art source for scenes** — the scene layer gains the
  ability to render a placed object from a WebP + sidecar instead of an SVG template,
  with identical placement, depth, binding and overlay behaviour.
- **A production and acceptance pipeline** — a locked camera/light rig, batch
  production by material family, a documented rejection library, and an acceptance
  check run before any asset enters the repo.
- **First-pass kit scope: 36 assets** — 8 shared, 7 residential, 9 agriculture,
  6 data centre, 6 water.

**Non-goals:**

- State variants. Neutral render only; `pump_running.webp` is a rejection, not an
  asset. All state lives in the SVG overlay layer, which already exists.
- Night variants, unless a vertical ships a day/night backdrop.
- Replacing the SVG templates. Both sources coexist behind one object interface.
- Commissioning an artist or purchasing a symbol library — a sourcing decision that
  follows this specification, not one this change makes.

## Capabilities

### New Capabilities
- `isometric-asset-kit`: the normative camera, lighting, output and material
  specification for kit assets; the footprint/socket/overlay-zone sidecar format;
  asset acceptance and rejection criteria; and the scene layer's ability to render a
  raster object as a placed scene object.

### Modified Capabilities
None. The scene document, binding layer and depth ordering are unchanged — a raster
object is placed by the same rules as an SVG template object, which is the point of
keeping art free of state.

## Impact

- **Depends on**: `add-spatial-scene-viewer` (object interface, placement,
  depth ordering, overlay layer). Blocked until its task 7.4 verdict.
- **Assets**: new `web/public/kit/<vertical>/<object>.webp` plus a `.json` sidecar
  per asset, at 512px delivered with 1024px retained for wall displays.
- **Frontend**: a raster object renderer in `web/src/components/Scene/`, reusing the
  existing overlay primitives (`WaveLevel`, `Spinner`, `ArcSweep`, `DashFlow`,
  `PulseRing`) drawn into the sidecar's declared overlay zones.
- **Cost**: the reason this change is gated. 36 assets at 1.5–3 artist-hours each
  once a rig exists; image-model generation is far cheaper per attempt but has no
  seed parameter, so an asset cannot be reproduced identically later — every source
  prompt and reference image must be committed alongside its output.
- **No runtime dependencies added.** Rive remains unadopted.
- **IP**: purely model-generated images with no meaningful human creative
  contribution may not be copyrightable. If the kit is intended to be defensible IP,
  that needs advice before production, not after.
